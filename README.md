## Custom Build (VoronBrothers)

<p align="center">
  <img src="docs/ollama-logo.svg" alt="ollama llama logo" width="120"/>
</p>

Форк Ollama с кастомными функциями для tmux-оркестрации. База — upstream `v0.34.0 ` где произошло разделение философии оллама.
Мы подхватываем новые фичи из новых версий оллама, держим руку на пульсе.
Наша цель - многочасовая эффективная работа клиентов с полным доступом к системе, чтобы агент чувствовал себя в системе как у себя дома (все риски на пользователе или ограничивайте доступ через shift + tab).

> **Сборка и установка.** Форк собирается из исходников, бинарники с ollama.com его не включают.
> Сборка всегда всех трёх бинарников (`ollama`, `lama`, `bee`) — скриптом **[`scripts/voron-build.sh`](scripts/voron-build.sh)**:
> сам определяет версию `<upstream>-voron-<DDMMYYYY>`, ставит `-tags sqlite_fts5` и ldflags,
> делает бэкапы и атомарную подмену (`sudo mv`, не `cp`).
> Правила версионирования, systemd drop-in'ы и ручной вариант — в [VORON-RUNBOOK.md](VORON-RUNBOOK.md).

### Поведение по умолчанию

- **Низкий effort размышлений** — если уровень thinking не задан явно, TUI использует `medium` (при medium пустой промт по стандарту llama.cpp ничего не придумали). Уровни: auto / on / off / low / medium / high / max (`/think`). Постоянный уровень на все сессии — `/think-forever <level>`.
- **Полный доступ к инструментам по умолчанию** — модель исполняет инструменты без подтверждения («full access»); переключение на режим проверки — `Shift+Tab`.
- **Очередь промптов** — можно слать несколько сообщений подряд во время генерации; они выстраиваются в очередь (`queued (N)`) и обрабатываются по одному.

### Авто-создание при первом запуске сервера

При старте `ollama serve` автоматически создаются (только если ещё не существуют, никогда не перезаписывают):

| Путь | Содержимое |
|------|------------|
| `~/.ollama/env` | Полный справочник переменных окружения — все закомментированы |
| `~/.ollama/providers.json` | Шаблон внешнего провайдера (заменить `YOUR_API_KEY_HERE`) |
| `~/.ollama/external_system_prompt.md` | Короткий универсальный системный промпт (EN) |
| `~/.ollama/chats/` | Пустая папка для `/save` |
| `~/.ollama/knowledge/` | Пустая папка для RAG-документов |

### Команды CLI: `run` устарел → `chat`

- **`ollama run …`** — депрекация: печатает «вызов устарел» и не стартует чат (сервер не нужен).
- **`ollama chat MODEL [PROMPT]`** — обычный чат без доступа к системе, но с функциями. Основан на оригинальной логике v0.34 (без кастомного буфера фоновых сообщений). Те же флаги, что раньше у `run`: `--think`, `--format`, `--insecure`, `--keepalive`, `--runner` и др.
- **One-shot (pipe)**: `echo "question" | ollama chat MODEL` — одноразовый запрос без TUI и памяти. Для proxy-моделей (`proxyapi/...`) автоматически используется `/api/chat` (а не `/api/generate`). Пример: `echo "2+2?" | ollama chat proxyapi/perplexity/sonar`
- В интерактиве `chat` работает `/add <пути...>` — прикрепить текстовые файлы (`.txt`/`.md`/`.py`/`.json`/`.jsonl`/`.yaml`/`.sh`/…) или **PDF с копируемым текстом** (извлечение через `pdftotext`, нужен `poppler-utils`) или папки (только верхний уровень); полное содержимое вставляется в контекст при отправке. Изображения не через `/add` — путь вставь текстом для vision-моделей.

### Быстрый запуск TUI: `lama`

Отдельный бинарник для мгновенного запуска полноценного TUI (bubbletea) без приветственного меню:

```bash
lama              # → TUI с моделью по умолчанию
lama llama3       # → TUI с моделью "llama3"
```

Модель по умолчанию — `envconfig.DefaultModel` (единый источник для всех бинарников,
override через env var `LAMA_MODEL`). Внутренне вызывает `cmd.LaunchModelTUI`, минуя welcome/menu.

**Собирается и ставится только вместе с остальными** — тем же `scripts/voron-build.sh`
(отдельная сборка lama быстро устаревает; прецедент 08.11: PDF в `/add` был только в одном бинарнике).
Вручную (только для отладки): `go build -tags sqlite_fts5 -ldflags "-X github.com/ollama/ollama/version.Version=..." -o lama ./lama/`

### TUI через CLI: `ollama tui`

Запуск полноценного agent-TUI (bubbletea + инструменты) прямо из `ollama` без отдельного бинарника.
Модель указывается явно в аргументе (в отличие от `lama`, где она берётся из env).
Спроектирован для **оркестрации**: встраивается в пайплайны, tmux-скрипты, цепочки команд.

```bash
ollama tui                          # подсказка + exit 0 (без интерактивного меню)
ollama tui lama                     # → TUI с моделью "lama"
ollama tui bread                    # model not found → stderr + exit 1
ollama tui lama 'продолжи работать'   # → TUI стартует, промпт авто-отправляется через ~1с
```

Pipeline-пример:
```bash
ollama stop; ollama tui lama 'ты продолжаешь задачу, контекст в /home/voron/.ollama/chats/123.json'
```

### Управляющие команды: `stop`, `ps`

| Команда | Действие |
|---------|----------|
| `ollama stop` / `ollama stop all` | Выгружает **все** модели из памяти |
| `ollama stop 1` | Выгружает модель под номером 1 в списке `ps` |
| `ollama stop <name>` | Выгружает модель по имени (как раньше) |
| `ollama ps` | Список запущенных моделей **с порядковым номером** (`#`) |

### Инструменты агента по умолчанию

`bash`, `bash_long`, `read`, `edit`, `write`; для мультимодальных моделей — `view_image`.
Опционально: `skill` (если есть каталог скиллов), `web_search` / `web_fetch`, MCP-серверы и `delegate`.
Отключение через переменные окружения, напр. `OLLAMA_AGENT_DISABLE_SHELL`, `OLLAMA_AGENT_DISABLE_WEBSEARCH`.

#### Личная shell-профиль агента (personal bash profile)

Инструменты `bash` / `bash_long` по умолчанию исполняются в **личном профиле**:

| Путь | Назначение |
|------|------------|
| `~/.ollama/agent/rc.sh` | Приватный rc: alias, функции, экспорт env — sourc-ится перед каждой командой |
| `~/.ollama/agent/history` | Лог всех выполненных команд (append-only, человекочитаемый) |

**Alias promotion**: все `alias` из `rc.sh` автоматически конвертируются в одноимённые shell-
функции, чтобы работали внутри неинтерактивного `bash -c` (обычный alias там не раскрывается).
Имена с дефисами пропускаются — для них используйте функции.

**Формат истории**: одна команда = одна строка вида `[YYYY-MM-DD HH:MM] <команда>`;
многострочные команды схлопываются в одну строку, чтобы лог оставался читаемым:

```
[2026-11-16 21:45] ls -la && cat foo.txt
```

**Выключение**: env var `OLLAMA_BASH_PERSONAL=off|no|0|false` → чистый bash без профиля и истории.

### Под-агенты: инструмент `delegate` + бинарник `bee`

`delegate` запускает под-агентов как отдельные живые tmux-сессии (бинарник `bee`).
Действия: `spawn` (старт с задачей), `list` (все агенты + ЯВНЫЙ статус), `status`
(подробно про одного), `models` (доступные «мозги»: облачные из `providers.json` +
локальные из `/api/tags`), `output` (хвост пейна, опц. `lines`), `stop`, `feed`
(сообщение до или во время работы), `pause`/`resume`. Под-агенты имеют полную
свободу; вы наблюдаете их вывод и направляете.

- **Модель «мозга»** — аргумент `model` в spawn; дефолт = `envconfig.DefaultModel`,
  override env var `BEE_AGENT_MODEL`. Перед спавном модель проверяется (guard):
  нет ни в providers, ни локально → явная ошибка вместо тишайшего 404 внутри сессии.
- **Инструменты под-агента**: `run_command` (персистентный bash, опциональный
  `timeout` 60–900 с, дефолт 120 — та же семантика, что у `bash_long`),
  `read` / `write` / `edit` — прямые file-инструменты без round-trip через shell.
  Долгая сборка больше не убивает агента: каждые 10 с в пейн печатается
  прогресс-строка, а результат приходит с префиксом
  `[Time: … | Duration: … | Since last run_command: …]`.
- **Бюджет раундов** — 300 tool-loop итераций на запрос (сброс при supervisor correction).

#### Статус под-агента — всегда явный

`bee` пишет state-файл (`/tmp/bee-state/<session>.json`, путь передаётся через
`BEE_STATE`) и обновляет heartbeat каждые 5 с. `delegate list` / `status` / `output`
читают его и показывают одну из строк:

| Строка | Значение |
|---|---|
| `▶ WORKING (round N, tool X) · phase for 12s` | агент реально работает сейчас |
| `✅ FINISHED (task done, N round(s), final answer)` | задача выполнена, процесс ждёт новую |
| `🛑 STALLED (no heartbeat 50s; last: …)` | процесс есть, но не подаёт признаков жизни |
| `💀 DEAD (tmux session gone, no heartbeat …)` | агента убили / он умер |
| `❌ FAILED: http 500 …` | ошибка модели или фатальный сбой |
| `⛔ STOPPED: max rounds (300) reached` | кончился бюджет раундов |
| `⏸ PAUSED (frozen N pid)` | заморожен через `delegate pause` |
| `⚠️ ORPHANED (tmux pane gone, brain pid N still alive — stop it)` | tmux-пейн умер, а «мозг» (PID из state-файла) живёт как отцепленный процесс: heartbeat пишет, но задачу не примет, пока его явно `stop`нуть |
| `👻 GHOST (no state file, tmux gone, brain pid N alive — stop it)` | ни state-файла, ни сессии в tmux — а живой «мозг» найден сканом `/proc` по env; виден только после ghost sweep

`output` дополнительно приписывает однозначную строку для основной модели:
`⏳ AGENT IS STILL WORKING` / `✅ AGENT HAS FINISHED` / `❌ AGENT IS NOT RUNNING`.

#### Почему под-агенты раньше «вылетали»

Две причины, обе устранены:

1. **`kill 0` на таймауте.** Персистентный bash агента жил в одной process group
   с самим `bee`; по таймауту (30 с — любая сборка) в шелл писалось `kill 0`, что
   убивало всю группу вместе с `bee` → tmux-сессия закрывалась, выглядело как
   `tmux kill-server`. Теперь шелл запускается с `Setpgid` в собственной группе,
   убивается только его дерево, а после таймаута шелл перезапускается.
2. **Самоубийственная команда от модели.** `tmux kill-server`, `killall tmux`,
   `pkill -f tmux`, `kill 0`, `killall bash` внутри `run_command` сносили сервер
   вместе со всеми сессиями. Такие команды теперь отклоняются с объяснением
   (см. `bee/guard.go`).

#### Ghost sweep и session-wide stop: невидимые «мозги» больше не выживают

«Мозг» под-агента (`bee`) запускается в собственной process session
(`setsid`), поэтому смерть tmux-сессии, крах tmux-сервера или перезагрузка
**не убивают его**: state-файл стёрт, сессия исчезла из `tmux list`, а процесс
продолжает работать «невидимо». Раньше такой агент показывался ложным
`💀 DEAD`, а `stop` не находил чего убить (0 процессов) — мозг выживал.

**Ghost sweep** (`delegate_ghost.go`). Источник истины — не tmux list и не
state-файлы, а процессы в памяти: `findGhosts()` сканирует `/proc/<pid>/environ`
и находит живые мозги по env `BEE_STATE`/`BEE_SESSION`, которые мы экспортируем
при spawn. Найденных агентов `sweepGhosts()` **adopt'ит в реестр** этой сессии:
после этого они видны в `list` со статусной строкой (`⚠️ ORPHANED` / `👻 GHOST`),
a `stop`/`feed` работают по id. Sweep ещё и **backfill'ит `brainPid`** для
агентов, которые создал сам `spawn()` этой сессии (раньше у них pid мозга не был
записан — ghost без state-файла оставался невидимым: ложный `DEAD`, `stop`
убивал 0).

**Session-wide stop** (`delegate.go::stop`). Ключевая ловушка: `tmux kill-session`
шлёт сигналы **только прямым детям** пейна, а setsid-мозг и его дети живут в
чужой session и выживают как сироты. Поэтому `stop`:
1. снимает дерево процессов **до** убийства сессии (корень = pid пейна);
2. явно убивает это дерево (`kill -9` по каждому живому, не-zombie);
3. находит pid «мозга» (из state-файла или backfilled `brainPid`) и бьёт
   сначала по всей его process group (`kill -9 -pid`), а если мозг — настоящий
   **session leader** (`sess == pid` из `/proc/<pid>/stat`) — дополнительно
   добивает все pids этой session: дети `run_command` могут жить в собственных
   пgrp внутри той же session и пережить `-pid`. Убьём чужую сессию мы не
   зацепим (она leader'а не своего).

Живость процесса проверяет `procAlive()` — zombie-safe: zombie (`Z`) уже мёртв,
просто не собран репетитором, и считается мёртвым.

### TUI: перманентный индикатор "Working"

Пока модель активна (`running == true`), внизу отображается постоянная строка:
```
○ Working [thinking ↓ 150]    ● Working [bash]    ◉ Working [out ↓ 42]
```
- **Пульс** (○ ◉ ●) — «сердцебиение»: круг наполняется и опустошается
  (~1.4 с/кадр, полный цикл ≈ 5.6 с) — спокойно, без стробоскопа.
- **Фаза** показывает текущий режим: thinking / tool name / out streaming.
  Имя инструмента остаётся видно даже после быстрого инструмента (edit/write)
  — до тех пор, пока модель обрабатывает его результат.
- **Stall warning**: если >15с нет ни одного события от модели → `⚠️ no data 18s`.
  Подавляется, пока активен инструмент или ожидается ответ модели —
  тишина в этих состояниях нормальна.

- **Очередь сообщений** показывается СПРАВА от индикатора, одной строкой:
  `● Working [bash]  ·  ⏳ queued (2): текст первого…`. Раньше во время
  генерации строка `queued (N)` исчезала совсем (индикатор перебивал её),
  и было непонятно, встало ли сообщение в очередь.

Индикатор виден во всех фазах (thinking, tool execution, chat streaming) —
не исчезает при переходах между режимами.

### Внешние провайдеры (external API)

Форк умеет проксировать модели внешних API-провайдеров через тот же `/api/chat`,
что и локальные. Конфиг — обычный JSON рядом с остальными настройками Ollama:
`~/.ollama/providers.json`.

```json
{
  "providers": [
    {
      "name": "proxyapi",
      "base_url": "https://api.proxyapi.ru/v1",
      "api_key": "sk-...",
      "models": ["qwen/qwen3.8-27b", "deepseek/deepseek-v4.1-flash-1017"],
      "context_window": 131072,
      "context_windows": {"qwen/qwen3.8-27b": 262144}
    }
  ]
}
```

- `name` — первый сегмент имени модели в API (`proxyapi/qwen/qwen3.8-27b`);
  сравнивается без учёта регистра;
- `base_url` — база OpenAI-совместимого API (хвостовой `/` отбрасывается);
- `models` — список `vendor/model`, как их ждёт провайдер; именно эти имена
  видны в `/api/tags` и в пикере `/model` с префиксом `<name>/`;
- `context_window` (необязательно) — окно контекста в токенах по умолчанию для
  всех моделей провайдера;
- `context_windows` (необязательно) — per-model переопределение:
  `{"qwen/qwen3.8-27b": 262144}`; регистр не важен, значения ≤ 0 отбрасываются.
- модели с префиксом провайдера уходят во внешний API, локальные — нет
  (ветка `tryParseExternalModel` в `server/providers.go`).

Зачем `context_window`: внешний API не отдаёт размер окна (в ответе
`/v1/models` только `id`/`owned_by`). Значение из конфига попадает в
`details.context_length` ответа `/api/show`, оттуда — в бюджет компактора.

Для **внешних API-моделей** TUI-агент по умолчанию поднимает окно до ~10 млн
токенов (даже без `context_window`), поэтому история почти не сжимается и
`/zip off` для них, как правило, не нужен. Это влияет только на внешние
провайдеры; локальные и ollama.com cloud модели используют своё реальное окно
(running num_ctx / рекомендация) и уплотняются по-прежнему. Точное (обычно
меньшее) значение для API задаётся `context_window`.

Автосжатие контекста можно выключить на время сессии TUI: `/zip` (алиас `/зип`)
переключает его, `/zip on|off` задаёт явно. По умолчанию — включено. При
выключенном автосжатии компактор остаётся доступен вручную (`/compact`), а
бюджеты обрезки вывода инструментов по размеру окна продолжают работать.
Состояние живёт в рамках запущенного TUI и переживает переключение модели.

Порядок поиска файла (`providerConfigPaths()`, `server/providers.go`):
1. `$OLLAMA_PROVIDERS_CONFIG` — если задан, **только** он (без фолбэков);
2. `$OLLAMA_HOME/providers.json`, иначе `~/.ollama/providers.json`;
3. `/etc/ollama/providers.json` — системный фолбэк.

Демон работает под `User=ollama` с чужим `$HOME`, поэтому путь в `/home/<user>`
требует drop-in с явным путём и ACL на каталог:

```bash
# /etc/systemd/system/ollama.service.d/providers.conf
# [Service]
# Environment="OLLAMA_PROVIDERS_CONFIG=/home/voron/.ollama/providers.json"

sudo setfacl -m u:ollama:x  /home/voron
sudo setfacl -m u:ollama:rx /home/voron/.ollama
sudo setfacl -m u:ollama:r  /home/voron/.ollama/providers.json
sudo systemctl daemon-reload && sudo systemctl restart ollama

sudo journalctl -u ollama -n 50 | grep -i providers
# providers: config loaded path=/home/voron/.ollama/providers.json
# providers: loaded external provider name=proxyapi models=2
curl -s http://127.0.0.1:11434/api/tags | grep proxyapi
```

Файл держим обычным файлом (не симлинком) с правами `600`/`640`: ключи не должны
быть доступны другим пользователям.

### Системный промпт для внешних моделей

Универсальный промпт применяется **только** к моделям внешних провайдеров;
локальные модели не затрагиваются ни на одном пути.

Файл (первый найденный побеждает):
1. `$OLLAMA_EXTERNAL_SYSTEM_PROMPT` — если задан, другие пути не смотрятся;
2. `external_system_prompt.md` в каталоге конфига провайдеров;
3. `system_prompt.md` там же (алиас).

Каталог конфига (`externalPromptConfigDir()`, `server/external_prompt.go`):
`dirname($OLLAMA_PROVIDERS_CONFIG)` → `$OLLAMA_HOME` → `~/.ollama`.
То есть промпт лежит рядом с `providers.json`: `/home/voron/.ollama/external_system_prompt.md`.

```bash
# правки подхватываются без рестарта демона (кэш по mtime + размеру)
# но можно и релоад демона чтобы быстрее подхватились модели апи и промт апи
nano ~/.ollama/external_system_prompt.md
ollama show proxyapi/qwen/qwen3.8-27b   # блок System
```

Куда попадает промпт:
- `buildOpenAIRequest` — первым сообщением `role: system` в исходящем запросе;
  если клиент уже прислал system с этим текстом — не дублируется, если прислал
  свой system — склеивается как `промпт + "\n\n" + свой`;
- `ShowHandler` — внешняя модель отдаёт промпт в `ShowResponse.System`, поэтому
  TUI включает его в запрос и показывает в `/system`;
- `/system off` в TUI отключает его и для внешних моделей.

Промпт общий для всех провайдеров; per-provider override пока нет.

### Spillover (экономия токенов)

Большие выводы инструментов (>~15k символов) автоматически сохраняются в файл
`$TMPDIR/ollama-spill/{hash}.txt` (на Linux: `/tmp/ollama-spill/`), а в контексте остаётся preview + путь.
Модель решает, читать ли полный вывод через file tool.

### Service

TUI: пункт меню **Service** — сервисные операции.
Подпункты:
- **Recreate env vars (~/.ollama/env)** — записывает в `$HOME/.ollama/env` полный справочник переменных окружения (все известные бинарнику: сервер, клиент, модели, GPU, дебаг, агент, провайдеры, сеть). Строки **закомментированы** — файл ничего не переопределяет, пока переменную не раскомментируют. Подтверждение y/n, sudo не нужен. Приоритет: process env > `~/.ollama/env` > `/etc/ollama/env`.
- Полнота справочника защищена тестом `envconfig/reference_template_test.go` (сверка с `envconfig.AsMap()`).

### База знаний (RAG)

Каталог `~/.ollama/knowledge/` для документов (`.txt`, `.md`, **`.pdf`** — извлечение через `pdftotext`).
Инструмент `knowledge_search`: BM25-поиск по чанкам (~500 слов, overlap 10%), хранится в SQLite FTS5.
TUI: пункт меню «Knowledge base / RAG» → `i` = индексация now, `o` = открыть папку.

Короткие клавиши: `Alt+Enter` — перенос строки; `Shift+Tab` — режим доступа; `Ctrl+O` — детали транскрипта; `↑/↓` — предыдущие промпты.
